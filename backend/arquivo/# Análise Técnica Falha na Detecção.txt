# Análise Técnica: Falha na Detecção de Tool Calls

## 📋 Resumo Executivo

**Problema Identificado:** 94.7% das tarefas (71/75) não estão detectando tool calls, mesmo quando o modelo gera tokens e responde adequadamente.

**Causa Raiz:** O modelo **qwen3.5:4b** está retornando tool calls em um formato que não está sendo corretamente parseado pelo código atual do `ollama_client.py`.

### 2. Padrão de Tokens Gerados

### 3. Análise do Código (`ollama_client.py`)

O método `chat_com_tools_stream_com_metricas` extrai tool calls assim:

```python
tool_calls = message.get("tool_calls")
if not isinstance(tool_calls, list) or not tool_calls:
    continue

tool_call = tool_calls[0]
function = tool_call.get("function")
name = function.get("name")
arguments_raw = function.get("arguments", "{}")
```

**Problema:** O código assume que `tool_calls` virá no formato estruturado da API do Ollama, mas o modelo qwen3.5:4b pode estar:
1. Retornando tool calls como texto no campo `content`
2. Usando um formato diferente do esperado
3. A estrutura `tool_calls` pode estar em outro nível do JSON

### 4. Fallback Textual Já Existe

O código já possui uma função `_tentar_extrair_tool_call_textual()` que tenta extrair tool calls do conteúdo textual:

```python
def _tentar_extrair_tool_call_textual(conteudo: str) -> dict | None:
    # Procura padrão JSON com "name" e "arguments" no content
    match = re.search(r'\{.*"name"\s*:\s*"[^"]+".*"arguments"\s*:\s*\{.*?\}\s*\}', conteudo, re.DOTALL)
```

**Porém**, esta função só é chamada no método `chat_com_tools_stream()`, **NÃO** no `chat_com_tools_stream_com_metricas()`.

---

## 🎯 Hipótese Principal

O benchmark está usando o método `chat_com_tools_stream_com_metricas()` (via `maria_runner.py`), que:
1. ✅ Captura `eval_count` corretamente (tokens_gerados = 52-66)
2. ✅ Captura conteúdo textual (`partes_texto`)
3. ❌ **NÃO** aplica fallback textual para tool calls
4. ❌ **NÃO** verifica se o modelo vazou a tool call no `content`

Quando o modelo retorna tool calls embutidas no texto (comum em modelos menores como qwen3.5:4b), o código descarta essa informação e retorna `tool_call_final = None`.

---

## 🔧 Soluções Propostas

### Solução 1: Adicionar Fallback Textual ao `chat_com_tools_stream_com_metricas`

**Arquivo:** `/workspace/core/ollama_client.py`

**Modificação:** Após o loop de streaming, adicionar:

```python
# Fallback: tentar extrair tool call do conteúdo textual
if tool_call_final is None and partes_texto:
    conteudo_acumulado = "".join(partes_texto)
    tool_call_textual = _tentar_extrair_tool_call_textual(conteudo_acumulado)
    if tool_call_textual is not None:
        logger.warning(
            "Tool call detectada via fallback textual: %s",
            tool_call_textual["name"]
        )
        tool_call_final = tool_call_textual
```

### Solução 2: Verificar Formato Alternativo do Ollama

O Ollama pode estar retornando tool calls em formato diferente. Adicionar logging temporário:

```python
# Dentro do loop, após parsear o JSON
logger.debug("Data chunk: %s", json.dumps(data, indent=2)[:500])
```

Isso revelará a estrutura exata que o Ollama está retornando.

### Solução 3: Ajustar System Prompt

O system prompt pode não estar incentivando suficientemente o uso de tool calls estruturadas. Revisar o prompt em `/workspace/core/chat_session.py`:

```python
SYSTEM_PROMPT = """...
IMPORTANTE: Quando o usuário pedir para criar planilhas ou documentos,
USE SEMPRE as ferramentas disponíveis (criar_planilha, criar_documento).
Não apenas descreva o que faria - CHAME a ferramenta explicitamente.
..."""
```

### Solução 4: Testar com Modelo Diferente

O qwen3.5:4b pode ter limitações com function calling. Considerar:
- qwen3.5:7b ou superior
- llama3.1:8b (melhor suporte a tools)
- mistral:7b-instruct
